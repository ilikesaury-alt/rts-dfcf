### A2 · 展示层同时承担业务、持久化、渲染三种职责

`display.build_scan_view`（381 行 / CC 77）内部做了三件性质完全不同的事：

- **业务**：排序、档位判定（`composite_tier`）、减仓标签过滤、不追涨门；
- **持久化**：`display.py:1073` 调 `decision_lines()` → 写 `decision_picks` 表（注释自称"与纯计算的约定冲突"）；
- **渲染**：拼装 `ScanView`。

**不合理之处**：一个叫 `build_scan_view`（"只算不画"）的函数会写数据库。这让它既不能当纯函数单测，也不能被复用（比如将来出 HTML 报告时，会连带触发一次决策落库）。

**连带问题：跨模块导入私有符号 21 处**，其中 `display.py` 一个文件就从 `ranking` 导入了 5 个 `_` 私有函数（`_entry_dims` / `_is_nextday_marked` / `_fresh_candidate` / `_breakout_profile_key` / `_breakout_structure_ok`）+ 从 `core_themes` 导入 `_low_buy_quality`。

```
scanner/display.py:28    from scanner.core_themes import _low_buy_quality
scanner/display.py:52-58 from scanner.ranking import _breakout_profile_key, _entry_dims, ...
scanner/walkforward.py:26 from scanner.ranking import _entry_dims, _entry_tier, _is_nextday_marked
scanner/historical_rescan.py:80 from scanner.enhancer import _apply_gap_up_bonus, _set_risk_flags
scanner/portfolio_backtest.py:65 from scanner.nextday_rule import _compute_features
```

下划线是"别碰"的约定，但实际有 21 处在跨模块使用 → **`ranking` / `enhancer` / `nextday_rule` 的内部结构事实上是公共 API，却没有任何东西保护它**。重构这些模块的内部实现会静默破坏 display 和 4 个 scripts。

**建议**：
1. 拆 `scanner/view/{model.py, assemble.py, render.py}`：`assemble` 收 dict 返回 dataclass（可单测），`render` 只负责把 dataclass 变文本。
2. `decision_lines` 的落库从视图层移出，回到主循环（或显式改名为 `build_and_persist_decision`，让副作用出现在函数名里）。
3. 被跨模块使用的 `_x` 函数**要么升为公共名，要么移到真正该在的模块**。逐个处理，别一次性大改。

### A3 · 两套档位系统并存 → 展示口径与复盘口径分叉

| 档位函数 | 消费方 |
|---|---|
| `ranking.composite_tier`（ranking.py:784） | `display.py`（**实时展示排序**） |

**不合理之处**：你在终端看到的档位，和复盘统计出来的档位，**不是同一个函数算的**。这类不一致不会报错，只会产生"为什么复盘说这票是档0、当时终端显示的却不是"这种查不动的问题。

**建议**：明确指定一个为准（从消费面看 `_entry_tier` 是历史口径，`composite_tier` 是展示口径）。让另一个成为显式的转换层或标记 `legacy`，并在测试里锁定「两者对同一输入的分歧是已知且被枚举的」，而不是靠人记得。

### A4 · fail-open 纪律名不副实（文档说的比代码严）

项目在多处注释里强调：**「本模块所有降级分支只捕获 `EXTERNAL_FAILURES`，不再用 `except Exception`，编程错误必须冒泡」**（`orchestrator.py:60-65`、CORE-FLOW §9.2）。

实测：全仓 **86 处 `except Exception`**，集中在数据层：

```
scanner/db/dal.py       20 处
scanner/db/queries.py   13 处
unified_scanner.py       7 处
scanner/data_source.py   6 处
today_report.py          5 处
```

而且 `EXTERNAL_FAILURES` 自身的定义（`scanner/utils.py:17-23`）包含 **`ValueError` 和 `KeyError`**：

```python
EXTERNAL_FAILURES = (OSError, socket.timeout, sqlite3.Error,
                     ValueError,   # JSON 解析失败 / 脏值强转
                     KeyError)     # 上游响应结构缺字段
```

**不合理之处**：`KeyError` 也是"我们把字典 key 拼错了"的报错，`ValueError` 也是"我们转换逻辑写错了"的报错。把它们和"外部依赖抖动"放进同一个元组，等于**允许我们自己的 bug 伪装成外部故障被吞掉**。而 `dal.py` 的宽泛捕获更进一步——批量写失败会静默降级为逐行写（N 次写 + 部分行丢失），只留一行 `logger.warning`。

**建议**（2026-09-13 已执行，见 §六；执行中修正了原判断）：

1. ~~收窄为 `sqlite3.Error` / `OSError`~~ → **修正为按"try 体内还有没有别的逻辑"二分**：
   - try 体内**只有** execute/executemany/commit/rollback → 收窄 `sqlite3.Error`（等价行为）；
   - try 体内含计算（统计清洗/契约校验）、或承担**批量→逐行回退**、**单行错误隔离**语义
     → 保留宽捕获，但必须带注释说明属于哪一类。
   一刀切收窄是错的：实测发现 `get_market_extra_cache` 的宽捕获**隐式承担了
   `conn=None` 的降级契约**（`fundamentals.get_fund_risk_from_db` 依赖它吞掉
   AttributeError），收窄后测试立刻红。正确修法是把契约**显式声明在定义它的地方**，
   而不是依赖下层宽捕获。
2. 保留 `ValueError`/`KeyError` 的捕获点，**逐处加注释说明"这里为什么可能由外部数据触发"**；说不出理由的，改窄。
3. **BLE 规则暂缓**：实测现有宽捕获有 86 处、分布在 20+ 文件，直接开启需要 75+ 处
   `# noqa` 或逐处行为判定，不是"零成本"。需先完成第 1 步的二分清理，再按文件收口。

### A5 · schema 迁移靠"现场探测"，没有版本化编排

`scanner/db/schema.py:52` 的 `init_db` 337 行，15 个迁移块线性堆叠，靠 `PRAGMA table_info` 探测当前状态来决定跑不跑。

实测生产库 `schema_version` = **`[1, 2, 4, 5, 6]`** —— 乱序、跳号，且 **v7 尚未应用**（`hot_watch_hits` 表不存在，任何读该表的离线工具现在会直接报错）。

表结构实际是「`CREATE TABLE` 基线 + 13 个 `ALTER TABLE ADD COLUMN`」拼出来的：

```sql
CREATE TABLE recommendations (... , excluded INTEGER DEFAULT 0,
  sector_capped INTEGER DEFAULT 0, stale_kline INTEGER DEFAULT 0,
  excluded_reason TEXT, nd10_pct REAL)   -- 后半截全是后加的列
```

**不合理之处**：09-11 修掉的那个「迁移静默跳过、永不重试」高危缺陷，**是这种结构的必然产物**，不是偶然。探测式迁移在"执行到一半中断"的场景下无法正确恢复。

**建议**：引入迁移列表 + 已执行记录表（`refactor-plan` 已给出方案，尚未落地）：

```python
MIGRATIONS = [Migration(id="m001_...", up=...), ...]
applied = {r[0] for r in conn.execute("SELECT id FROM schema_migrations")}
for m in MIGRATIONS:
    if m.id in applied: continue
    m.up(conn)   # 单事务 + 失败上抛
    conn.execute("INSERT INTO schema_migrations VALUES (?, ?)", (m.id, now))
```

**注意**：这涉及生产库，**最后做**，且先 `cp scanner.db`。

## 二、B 组：方法论问题（比 A 组更致命）

### B1 · 样本量与参数面严重失衡 —— 这是项目真正的瓶颈

实测归因样本口径（`recommendations`，`excluded=0` + 同票同日去重）：

| 指标 | 实测值 |
|---|---|
| 总行数 | 5,070 |
| 交易日数 | **76** |
| 不同 symbol | 637 |
| (date, symbol) 组合 | 2,720 |
| (date, symbol, category) 组合 | **3,080** |

对照参数面：

| 参数面 | 数量 |
|---|---|
| `config.py` 模块级常量 | **395**（1,083 行） |
| 评分/决策核心的数值字面量 | **1,131**（enhancer 75 / analysis 249 / ranking 106 / validator 167 / matcher 88 / weights 84 / core_themes 123 …） |

**不合理之处**：**~3,000 个有效信号 vs ~1,500 个可调数值**。而且这 3,000 个信号**远非独立**——同一只票在 76 天里反复出现（637 个 symbol 产生 2,720 个组合），同日信号高度相关。

更具体的风险：每日样本量分布是 **min=1 / median=38 / max=572**。按日聚合的统计（`prevday_perf` 的"档位 → 次日表现"）会让**一个只有 1 个样本的交易日和一个 572 个样本的交易日等权**。

**这解释了一个已在项目里观察到的现象**：`nextday_prob.py` 的 docstring 自己写着「因子命中率随市场 regime 变化，本项目文档注释数字**已两次过期**」。这不是文档维护问题，是**参数多于信息量**的典型症状。

**建议**（按性价比排序）：
1. **先建立样本外纪律**：任何权重/阈值改动，必须在 walk-forward 的样本外窗口上验证，
   且记录"改动前后"的样本外表现。**2026-09-13 复核修正**：项目虽有三个相关工具
   （`walkforward` / `rule_change_tracker` / `portfolio_backtest`），但**没有一个回答
   「这个改动是真信号还是噪声」**——故新建 `scanner/rule_validate.py` 作为验证门，
   详见 §6.6。
2. **按日聚合加权**：日级统计改为按日等权（先算每日指标再平均），避免小样本日扭曲。
   `rule_validate` 已按此口径实现，并打印两种口径的差值以量化扭曲量（实测 +1.8pp）。
3. **冻结参数面增长**：新因子入库前必须证明"样本外有增量"，而不是"样本内 IC 更高"。
4. **不要继续加因子**。当前 5 桶 + v2 池选 + 回马枪 + 低吸已经 4 套并行体系，再加只会让归因更难。

### B2 · 概率模型的校准常数手工誊写、与数据脱钩 —— **已复核，比原判断更严重**

原判断（本节初稿）是"常数硬编码、无机制保证被复核"。**2026-09-13 实跑复核后升级为：
已经发生了实质性的口径错误，且没有任何测试能发现。** 证据链：

**(1) `OR_MARKED` 的拟合口径与线上判据不一致（确证）。**

`OR_MARKED = 2.6` 的 docstring 记着读数「marked 13.6% (n=543) vs unmarked 5.8% (n=794）」。
本次在**同一 09-05 日期子集**上按不同口径重算：

| 口径 | marked | unmarked | OR |
|---|---|---|---|
| 甜蜜带 ∩ 非超买（**无累计门槛**） | 596 (12.8%) | 775 (**5.8%**) | **2.37** |
| 线上完整 `_is_nextday_marked` | 295 (12.2%) | 1076 (7.9%) | 1.62 |

第一行的 unmarked hit 与文档记载的 **5.8% 完全一致** —— 确认原常数是在
「甜蜜带 ∩ 非超买」口径下拟合的。但线上 `ranking._is_nextday_marked` 自
**2026-08-14** 起已含「5 日累计 ≥ `NEXTDAY_ACCUM_MIN`」门槛（该函数 docstring 明写）。
按线上真实口径在**全量样本**（2185 去重）重算：

```
marked 10.8% (n=344)  vs  unmarked 7.2% (n=1213)   →  OR = 1.56
```

**常数 2.6 相对真实口径高估 67%（odds 尺度）。** 更值得注意的是：
`nextday_prob.py` 的 docstring 原本把**正确口径**（「甜蜜带+累计≥6 hit 20%」）标注为
"更小样本期的读数，已失效"—— 这是把口径取反了，不是数据过期。

**(2) 涨幅带 4 个 OR 与 `OR_OVERBOUGHT` 存在同类错位（已量化，暂不改）。**

文档各带样本量之和 = 1786 = 全样本（605+411+556+214），说明它们是按
「全样本条件组 vs 全体样本」拟合的；而模型只对「未标记且非 short_term」行乘该 OR。
**参照组不是适用集合的补集**，OR 描述的不是模型实际乘上去的量。按适用集合重算：

| 常数 | 代码值 | 按适用集合实测 | 漂移 |
|---|---|---|---|
| `OR_OVERBOUGHT` | 0.68 | 0.84 | +24% |
| `OR_BAND_SWEET_LOW` | 0.88 | 0.690 | −22% |
| `OR_BAND_DEAD` | 0.70 | 0.806 | +15% |
| `OR_BAND_MID` | 1.35 | **2.040** | **+51%** |
| `OR_BAND_TRAP` | 1.07 | 1.091 | +2% |

**(3) 类别 base rate 末段普遍高估（纯数据漂移，同口径）。**

`core_dip` 0.089 → 实测 0.065（+37% 高估）、`pool_pick` 0.028 → 0.021（+33%）、
`_default` 0.078 → 0.068（+13%，未超容差暂留）。核心区（rebound / kNF / momentum /
new_face）漂移均 <4%，说明不是系统性口径问题，是这两个类别本身衰减了。

**(4) 没有任何测试能发现以上任何一条。** `tests/test_nextday_prob.py` 全部 10 个测试
**只断言因子方向与大小关系**（`p_marked > p_unmarked`、`OR_BAND_DEAD < 1.0` …），
唯一一处写死数值是 `math.isclose(BASE_RATE_DEFAULT, 0.078)`。本次复核前后该文件**全绿**。

**要肯定的**：这个模块的方法论自觉仍是项目里最好的——明确写了「P 是排序量不是预测值」、
拒绝了 3 个未验证因子、做了防重复计费、docstring 主动标注了每个常数的样本量。
问题不在设计意图，在**工程化落地**：数值正确性完全没有进入验证闭环。

**已执行的处置（详见 §6.5）**：
1. 新增 `scanner/nextday_calib.py` —— 校准重算 + 漂移巡检单源，每个因子的口径
   （适用行集合 + 参照组）显式声明在 `FACTOR_SPECS`，不再靠人眼读数手抄。
2. 新增 `scanner/nextday_calib.json` 快照 + `tests/test_nextday_calib.py`（8 个测试）
   —— 代码常数与快照不一致即 fail；快照过期（>45 天）即 fail；超容差漂移必须登记豁免。
3. 修正两处**确证的口径错误**：`OR_MARKED` 2.6 → 1.56、`OR_OVERBOUGHT` 0.68 → 0.84；
   刷新 `core_dip` 0.065、`pool_pick` 0.021。改动前经排序 A/B 验证（见 §6.5）。
4. 涨幅带 4 项**不改**，登记进 `ACKNOWLEDGED_DRIFT` 并写明解除条件。

**原建议 3（`n<100` 的 OR 强制收缩到 1.0）—— 经复核后不采纳**：`OR_OUTFLOW` 当前
n_cond=92、hit 1.1% vs 参照组 3.8%，是**全表最强的负向因子**（OR 0.277）。硬收缩到
1.0 会把最有效的风险信号抹掉。正确做法是「报告样本量 + 由容差与豁免机制管理」，
而不是按样本量一刀切——已在快照里逐项记录 `n_cond`/`n_ref`。

### B3 · 工具链有缺口，但成本最低

| 能力 | 实测状态 |

### 6.5 B2 的处置细节与验证证据

**为什么先做 B2 而不是 B1**：B1 需要先有"样本外 harness"这个基础设施；B2 的

**A/B 验证台**（`scripts/nextday_calib_ab.py`，可复现）：
影响面说明 —— 这些常数只参与 `final_pick` 的 `_p` 排序键（`ranking._entry_tier`
用的是 `_is_nextday_marked`，不经概率），所以影响面 = 终选 ≤2 只的顺序与集合。
以「排除 momentum 后按 `_p` 取前 2」为终选代理：

| 变体 | rank-IC | top-1 | top-2 | 改选日 |
|---|---|---|---|---|
| 基线（修正前代码，`OR_MARKED=2.6`） | 0.0516 | 12.2% | 23.0% | — |
| 仅 `OR_MARKED` → 1.56 | 0.0500 | **14.9%** | 24.3% | 9/75 |

| 仅涨幅带 → 实测 | 0.0474 | 13.5% | 23.0% | 5/75 |

**决策**：
- `OR_MARKED` / `OR_OVERBOUGHT` / 两项 base rate —— **改**。前三项都是口径纠错
  （不是调参），且头部指标不劣（top-1 12.2%→14.9%，rank-IC 基本持平或改善）。
- 涨幅带 4 项 —— **不改**。基线修正后重测（`scripts/nextday_calib_ab.py`）：
  换成实测值后 top-2 hit 23.0%→28.4%（+5.4pp，≈1.3σ，n=74 日**不显著**）
  而 rank-IC 由 0.0484 降至 0.0426 —— 头部指标与整体单调性**方向相反**，
  样本内证据不足以判定。已登记 `ACKNOWLEDGED_DRIFT` 并写明解除条件。

**这套验证台的方法论局限（必须说清）**：它是**样本内**的——候选常数值本身是从
同一批样本算出来的，因此对"按实测重算"的变体天然有利。它的正确用法是**证伪**：
若某个改动在样本内都不改善头部指标，就没有理由上生产（涨幅带 4 项正因"方向相反"
被否，而"改 base rate"虽 rank-IC 最好但 top-2 不动、属纯刷新）。**真正的样本外
证据仍需 B1。**

**为什么把 `n=92` 的 `OR_OUTFLOW` 留下**（原报告建议 3 被否决）：它是全表最强负向
因子（hit 1.1% vs 参照组 3.8%，OR 0.277）。按样本量一刀切收缩到 1.0 会把最有效的
风险信号抹掉。已在快照里逐项记录 `n_cond`/`n_ref`，由容差与豁免机制管理。

| `scanner.walkforward` | 「8 个**硬编码**因子谓词跨窗是否稳定」 | 检验的是固定结论，不检验"我这次改的常数" |
| `scripts/rule_change_tracker.py` | 「改动历史记录」 | 自述"退出码恒为 0，不阻断构建/提交" |
| `scanner.portfolio_backtest` | 「组合 P&L」 | 自述"**禁止**拿它去调权重" |

于是新建 `scanner/rule_validate.py`——**样本外验证门**。它的全部价值在三条纪律：

**(1) 样本外优先。** 滚动 train/test 窗（train 30 → embargo `WF_EMBARGO_DAYS`=1 → test 10，
步长 = test 窗，共 4 个窗），**判定只看 test 窗**；train 窗 Δ 一并打印，用于暴露过拟合。
embargo 复用 `walkforward` 的既有设计——next_day 标签 horizon=1，不空窗会让 train
见过 test 首日的答案。

**(2) 按日等权。** 日级统计先算每日指标再平均。工具同时打印两种口径的差值，**直接量化
B1 主论点**。实测（rescore 口径，test 窗）：

```
基线  日等权 7.1%  vs  行汇总 5.3%   差 +1.8pp
```

即：按行汇总会把结果**低估 1.8pp**（小样本日被大样本日淹没）。这正是 §B1 原文说的
"min=1 / median=38 / max=572" 造成的扭曲，现在有了可复现的数字。

**(3) 评估器可见性硬校验。** `--set` 改的模块若不在所选评估器的"可见集合"内，**直接
报错退出**（退出码 3）。实测：

```
$ python -m scanner.rule_validate --set scanner.config.MIN_SCORE=60
  [可见性错误] 以下改动不会被所选评估器看见，验证结论无效：
    - scanner.config.MIN_SCORE=60：改动模块 scanner.config 不在评估器 nextday-prob
      的可见集合内（可见：['scanner.nextday_prob']）→ 该改动不会体现在指标里，验证结论无效
EXIT=3
```

这条防线针对的是调参时**最常见的自欺**：验证了一个根本没生效的改动。三档评估器各自的
可见集合是显式声明的：

| 评估器 | 可见集合 | 覆盖 | 代价 |
|---|---|---|---|
| `stored-score` | 无（冻结分） | 仅作对照基线 | 快 |
| `nextday-prob` | `scanner.nextday_prob` | 终选层 `_p` 排序 | 快（默认） |
| `rescore` | config / weights / analysis / enhancer / validator / ranking / categories | 评分链改动 | 29s（重扫） |

**顺带解决的一个隐蔽陷阱**：项目用**快照式导入**（`from scanner.config import MIN_SCORE`
把值绑进导入方命名空间），只改 `scanner.config.X` 对 `analysis`/`candidates` 等消费方
**无效**。工具因此实现了 override **传播**（把"仍是旧值"的 `scanner.*` 副本一并改写）
与**逆序回滚**，并在报告里打印传播到的模块数。实测端到端：

```
$ python -m scanner.rule_validate --evaluator rescore --set scanner.config.NEW_FACE_MIN_SCORE=200
      scanner.config.NEW_FACE_MIN_SCORE=200  →  传播改写 1 个模块：scanner.candidates
  诊断 · 日等权 rank-IC：基线 -0.0300 → 改动后 -0.0268（Δ +0.0032）
```

rank-IC 确实变了 → 改动真的进了重扫管线（不是"验证了没生效的改动"）。

**结论（已写进代码，防止下一个人再"修正"它）**：这 4 个常数**是按终选目标校准的，

1. `scanner/nextday_calib.py` 的 `ACKNOWLEDGED_DRIFT` 三条豁免补上完整 B1 证据与结论；
2. `scanner/nextday_prob.py` 涨幅带 4 常数定义处加显式警告（含复核命令），

**这条结论本身也是 B1 的价值证明**：在没有样本外纪律时，"把错的口径改成对的实测值"
