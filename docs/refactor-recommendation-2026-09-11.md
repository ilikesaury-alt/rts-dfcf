## 零、诊断对重构方向的三点修正

### 修正 1：重构目标从「代码更好维护」改为「降低无效输出」

原方案把 `orchestrator.scan_with_raw`（507 行 / 复杂度 105）列为第一优先级，
理由是「它让策略实验变贵」。

**诊断后这个理由依然成立，但不再是第一优先。** 因为诊断发现：
**系统当前最大的问题是「输出了 100 只无决策价值的票」，
而不是「代码难改」。** 先解决输出，再解决可维护性 ——
否则我们只是把一个庞大的无效系统重构得更整洁。

### 修正 2：`display.py` 的地位大幅上升

诊断显示用户看到的是「85–143 只按无效排序排列的列表」。
`display.build_scan_view`（381 行 / 复杂度 80）正是**产生这个列表的地方**，
且它内部混着排序/档位/过滤逻辑。

**它从「第二优先」升为「第一优先」** —— 因为改它直接改变用户每天看到的东西。

### 修正 3：新增一个原方案没有的最高优先级 —— 「输出契约」

原方案没有涉及「输出什么」。诊断后这成为核心：

> 系统应当从「每天输出 100 只并排序」改为「每天输出 ≤3 只，或明确输出『今天不买』」。

这是一个**契约级改动**，涉及 `display` / `final_pick` / `decision` / `feishu` 四个模块。

## 一、修正后的漏斗（这是重构要解决的真实结构）

诊断查出从市场到决策的真实漏斗：

| 层级 | 规模 | 说明 |
|---|---:|---|
| 创业板标的 | ~988 | `daily_kline` 覆盖 |
| 飙升榜（当时总数均值） | ~99 | 数据源 |
| 其中创业板（`gem_listed`） | **~17** | 真正可选范围 |
| 每日产生推荐 | ~66 | 三类桶入库 |
| **每日实际展示** | **~64（85–143）** | ← **问题在这里** |
| 终选区上限 | 3 | `FINAL_PICK_MAX` |

### 关键矛盾

**候选池并不只来自当日飙升榜**，而是多源合成（这一点我一开始判断错了，
核对后修正）：

| 来源 | 说明 |
|---|---|
| 当日飙升榜 | 均值总数 99.3，其中**创业板仅 16.7**（中位 16，p75=20，max=29） |
| `watch_pool`（掉榜跟踪） | 436 行 —— 已掉出榜单但仍在跟踪的票 |
| 回马枪 / 池选 / 核心低吸 | 基于历史与概念，不要求当日上榜 |

近期（2026-08-19 起）推荐来源构成：

| 类别 | 条数 |
|---|---:|
| `pool_pick` | 432 |
| `core_dip` | 397 |
| `comeback` | 396 |
| `short_term` | 289 |
| `rebound` | 42 |
| `momentum` | 32 |
| `new_face` | 17 |
| `known_new_face` | 13 |

**这带来一个重要发现**：近 30 天推荐构成（按条数）：

| 类别 | 条数 | 均值 | 性质 |
|---|---:|---:|---|
| `comeback` | 467 | −0.155% | 掉榜跟踪（历史池） |
| `short_term` | 433 | **−1.018%** | 短线 |
| `pool_pick` | 432 | **−1.003%** | 池选 |
| `core_dip` | 397 | +0.239% | 历史池低吸 |
| `momentum` | 49 | −2.042% | 动量 |
| `rebound` | 46 | −0.426% | 反弹 |
| **`new_face`** | **18** | **+1.461%** | **当日新上榜** |
| `known_new_face` | 13 | −1.898% | 当日新上榜 |

（全历史口径：`new_face` n=1,036 +0.089%、`known_new_face` n=140 +0.735%）

**近 30 天里，真正基于「当日飙升榜新面孔」的类别合计仅 31 条（2.3%），
而基于历史池与概念的类别合计 1,296 条（97.7%）。**

> 也就是说：**系统近期的输出，几乎不是「今天飙升榜里有什么」，
> 而是「历史上跟踪过的票今天怎么样了」。**

用户的直觉（「看飙升榜抓次日大涨」）与系统的**实际行为已经严重偏离**。
更值得注意的是：偏离前后的收益都不好（三个主要类别 −1.018% / −1.003% / −0.155%），
而小样本的 `new_face` 反而 +1.461%（但 n=18，不足为据）。
**这提示「回到飙升榜本源」可能比继续扩展历史池更有希望** ——
但同样需要在冻结期后用样本外数据验证，现在不能下结论。

- 日均展示 **64.1 只**（远超当日创业板在榜数 16.7）；
- 展示的 64 只中，排序 IC = 0.012（无效）；
- 而终选区（≤3 只）是唯一有「准入逻辑」的部分，但：

| 区域 | 次日均值 | 3 日均值 | 样本 |
|---|---:|---:|---:|
| **终选区**（去重） | **−1.798%** | **−9.620%** | n=6 |
| 全池对照 | −0.782% | −1.420% | n=4,529 |

**终选区比它所筛选的全池更差。** 但必须说明：**n=6 太小**
（终选区 2026-09-04 才上线，仅 5 个交易日，
`decision_picks` 共 24 条记录 / 18 条标的 + 6 条门控空仓），
**不能据此断言终选无效，只能说「没有任何证据支持它有效」。**

不过有一点是确定的：**当前系统的两层输出（100 只列表 + 3 只终选）
都无法被数据证明优于随机。**

## 二、修正后的重构建议（按新优先级）

### 【P0】输出契约重构 —— 从「100 只」到「0–3 只」

**改什么**

1. **主表不再作为买入候选展示**。85–143 只的列表降级为
   「扫描记录」（可查询、可回看，但不在主界面等权呈现）。
2. **决策层/终选成为唯一主输出**，且允许并强调空仓：
   `decision.py:230` 已有 `✗ 空仓 — {gate_reason}` 的输出，
   实际 6 个交易日里有 **6 天门控空仓** —— 这个行为是对的，应当保持并强化。
3. **明确「今天不买」是合法输出**。当没有标的通过准入时，
   标题应直接写「今日无标的」，而不是给出 100 只让人自己挑。

**为什么这是 P0**

诊断的核心结论是「你在不赚钱的池子里用无效排序挑」。
**撤销这个列表，问题的一半（「不知道买哪只」）立刻消失** ——
因为不再有 100 个选项。

**风险与前提**

- 这会让「系统看起来什么都没给」。需要同时改 `feishu.py` 的推送文案，
  否则用户会以为程序坏了；
- **必须先做 P1 的验证**：如果终选区本身无效，缩减到 3 只只是
  把「广泛小亏」变成「集中亏」。所以 P0 与 P1 应当**并行推进**，
  P0 可以先做「降级主表」（低风险），P1 完成后决定终选区去留。

**涉及模块**：`display.py`（主表分区）、`decision.py`（空仓语义）、
`final_pick.py`（准入）、`feishu.py`（推送文案）

---

### 【P1】先冻结、再验证 —— 这是所有统计工作的前提

**改什么（不是写代码，是流程）**

1. **冻结规则 ≥20 个交易日**：不增删类别、不调阈值、不加因子；
2. 期间**记录每个决策的「事前理由」**（已有 `decision_picks.reason`，可复用）；
3. 冻结期后，用**样本外**数据检验：
   - 终选区是否真的优于全池？
   - 哪些类别/条件真正有正期望？

**为什么这是 P1 且不可跳过**

诊断已用数据证明：**因为类别一直在增删，历史数据不是同质样本**
（前半段与后半段符号相反：保留组 −1.082% vs +0.479%）。

> 在持续改规则的系统上做回测，测到的是规则的生命周期，不是规则的效果。

**所以「继续调参」在当前状态下没有任何意义。**
冻结是让后续任何验证有意义的最低前提 —— 这不是保守，是必要条件。

**注意：这项不是代码重构，但它应当排在代码重构之前。**
如果只允许做一件事，做这个。

---

### 【P2】`display.py` 拆层 —— 让「展示什么」可独立决策

**改什么**

`build_scan_view`（381 行 / 复杂度 80）同时承担：
排序、档位判定、减仓标签过滤、行构建、文本渲染。

拆为：

```
scanner/view/
  model.py      # ScanView / MainRow dataclass（纯数据）
  assemble.py   # 扫描结果 → ScanView（含排序/档位/过滤 = 业务规则）
  render.py     # ScanView → 终端文本（纯展示）
```

**为什么**

- P0 的「降级主表」需要改动视图组装逻辑 —— 当前它与渲染纠缠，
  改动风险高；
- 业务规则（什么该展示）与表现（怎么画）分离后，
  「今天该不该展示这 100 只」才能被单独讨论和测试。

**顺带修一个确定的隐患**：`_SELL_TAGS` 有**三份完全相同的字面量拷贝**
（`display.py:885`、`display.py:951`、`final_pick.py:73`），
且 `final_pick.py:73` 的注释写着「与 display 主表/v2 池选区同源」——
**实际是拷贝，注释在误导**。改一处忘另两处会造成展示与终选口径
静默不一致。应移入 `categories.py`（已是标签唯一真源）。

**风险**：中。`tests/test_display.py`（52 测试）直接调 `disp_mod.*` 公开函数，
多为行为断言（如 `fund_flow_signal` 的档位边界），重构后应可复用。
先确认无「断言具体行号/格式字符串」的脆弱测试。

### 【P3】`decision.py` / `final_pick.py` 的准入逻辑需可解释化

**改什么**

当前准入是：市场门（`GATE_INDEX_MIN_PCT` / `GATE_CUM5_MIN_PCT`）
→ 终选概率 P → 美感门 → 去相关。

**问题是每一环的有效性都未被验证**（`beauty_gate_eval.py` 甚至不存在，
`OR_*` 因子已过期且两个方向搞反 —— 见前期分析）。

建议：
1. **为每次准入决策记录完整快照**：哪个门拦下的、P 是多少、
   事后收益如何 → 写入 `decision_picks` 或新表；
2. 冻结期后，**逐门计算「拦截命中率」**：被拦的票事后真的更差吗？
3. 只保留「拦得对」的门。

**为什么不是现在就改逻辑**

因为现在改就是继续「在移动的靶子上调参」。
**先让它可观测，等冻结期结束再决定去留。**

> 顺带注意：`GATE_INDEX_MIN_PCT = 0.0` / `GATE_CUM5_MIN_PCT = -3.0`
> （`decision.py:51-52`）是两个**硬编码在模块内**的阈值，
> 而项目纪律要求阈值收口到 `config.py`。这是 P5 减法阶段应一并处理的。

### 【P3.5】重新审视「候选池来源构成」 ← 诊断新增

**诊断新发现**：近 30 天 97.7% 的输出不是来自当日飙升榜，
而是来自历史池跟踪（`pool_pick` / `comeback` / `core_dip` / `short_term`）。

**这是一个需要用户决策的问题**，而不是纯技术问题：

- 若目标是「抓次日大涨」→ 历史池跟踪的定位是什么？它为什么占 97.7%？
- 若历史池是必要的（补充候选量）→ 为什么它 3 个主要类别全为负？

建议在冻结期内**只做观测不做改动**：标记每个推荐的实际来源
（当日榜 / 掉榜跟踪 / 概念池），冻结期后按来源分别统计收益。
这能让「哪个来源真正有效」变得可回答 —— 而当前无法回答。

### 【P4】`orchestrator.scan_with_raw` 拆阶段 —— 原方案的 A 项，降为 P4

**理由变化**

原方案把它列为第一优先（507 行 / 复杂度 105）。
诊断后降为 P4，因为：

- 它的收益是「让策略实验变便宜」，但诊断的结论是
  **现在不缺实验速度，缺的是「实验能否被验证」**；
- 在规则冻结期，本来也不该做大量策略实验；
- 但它的**可维护性收益仍然真实**，应在冻结期内（不引入行为变化时）择机做。

**做法不变**：抽 `scanner/pipeline/`（build_pool / classify / scoring /
enrich / validate / persist），`scan_with_raw` 退化为 ~80 行编排。
用「同一 raw 输入 → ScanResult 逐字段一致」证明等价变换。

与 `docs/refactor-plan-2026-09-11.md` 中的方案一致，优先级不变（本就靠后）：

## 三、修正后的执行顺序

```
阶段 0 · 立即（不写代码）                          ★★ 最高优先
  ├─ 冻结规则 ≥20 个交易日（不增删类别/不调参/不加因子）
  ├─ 主表降级为「扫描记录」，不再作为买入候选清单
  └─ 强化「空仓是合法输出」的语义与文案

阶段 1 · 冻结期内（低风险代码工作，不引入行为变化）
  ├─ P2 display 拆层 + _SELL_TAGS 消多真源
  ├─ P3 决策记录可观测化（只加记录，不改逻辑）
  ├─ P3.5 标记推荐来源（当日榜 / 掉榜跟踪 / 概念池）
  └─ 补 CI lint 范围 + 覆盖率基线（原方案第 0 步）

阶段 2 · 冻结期结束（用样本外数据决策）
  ├─ 验证终选区是否优于全池 → 决定保留/重做/删除
  ├─ 逐门计算拦截命中率 → 删除无效的门
  ├─ 按来源统计收益 → 决定历史池跟踪的去留
  └─ 若确有效：再谈优化；若无效：回到「池子」而非「排序」

阶段 3 · 结构清理（原方案 P3/P4/P5）
  ├─ P4 orchestrator 拆 pipeline
  ├─ P5 config 拆分 + init_db 迁移版本化
  └─ 减法：清理无证据的常量/因子/类别
```

**关键：阶段 0 和 1 可以今天就开始，且阶段 0 不需要写任何代码。**

## 四、三条纪律（在诊断结论上收紧）

1. **先冻结，后验证，再优化。** 违反这个顺序的任何改动都是
   「在移动的靶子上调参」—— 诊断已证明这样做测到的是
   规则的生命周期而非规则的效果。
2. **重构不夹带行为变更**（沿用原方案）。
   但注意：P0 是**有意的行为变更**，应单独提交、单独说明。
3. **每一步都要能回答「我怎么知道它有效？」**
   如果答不上来，说明这一步不该做。

## 五、如果只做一件事

**做阶段 0 的第一条：冻结规则 20 个交易日。**

理由：诊断已经用数据证明，**当前任何基于历史的统计结论都不可信**
（前半段与后半段符号相反）。在这个状态下：

- 继续调参 → 无效（测的是生命周期）；
- 继续重构 → 只是把无效系统整理得更整洁；
- 继续加类别/因子 → 让数据更加非同质。

**冻结 20 天是唯一能让后续所有工作变得有意义的前提。**
它不需要写代码，不需要改架构，只需要**停止改动**。

如果只做两件事，第二件是**把主表降级**（P0）——
它直接消除「85–143 个选项」这个困惑来源。
