# 策略筛选滞后性优化计划（保守优化）

## Summary

用户感知到的滞后性主要表现为"票涨起来了才进推荐"。经探索，滞后有三个来源：(1) K 线双层缓存叠加导致打分用的 K 线最差可达 10 分钟前；(2) 早市 -5 惩罚把早盘异动票压在 MIN_SCORE 门槛下；(3) momentum 策略要求 5 日累计涨幅 ≥10%，今天刚启动的票无法进入 momentum 池。

本计划采用**保守优化**路线：仅缩短缓存 TTL、放宽早市惩罚、小幅下调 momentum 累计涨幅门槛。**不缩短主循环 60s 间隔**（避免触发雪球限流），**不增加 API 调用量**（K 线缓存去掉 API 层冗余，但保留编排层 TTL 实际净调用次数不变）。

## Current State Analysis

### 滞后源 1：K 线双层缓存叠加（最隐蔽）

- `scanner/api.py:93-94`：`_kline_cache_ttl = 600`（API 层，10 分钟）
- `scanner/orchestrator.py:77`：`KLINE_REFRESH_TTL = 300`（编排层，5 分钟）
- **问题**：编排层判定 >300s 需要补拉时，`fetch_kline` 内部还会检查 API 层缓存，若 <600s 直接返回旧数据。实际 K 线新鲜度上限最差 600s。
- **影响**：一只 10:00 异动的票，扫描器可能在 10:05 才用上 10:00 的 K 线打分，此时票已涨 3-5%，用户感知就是"涨起来了才推"。

### 滞后源 2：早市惩罚 + MIN_SCORE 叠加

- `scanner/config.py:323`：`EARLY_BONUS = -5`（9:30-10:30）
- `scanner/config.py:15-18`：`NEW_FACE_MIN_SCORE=18 / MOMENTUM_MIN_SCORE=16 / PULLBACK_MIN_SCORE=18 / SHORT_TERM_MIN_SCORE=15`
- **问题**：早市 -5 等效于把 momentum 门槛从 16 提到 21、new_face 从 18 提到 23。早盘异动但分数刚过门槛的票会被压下去，要等 10:30 后惩罚消失才进推荐。
- **影响**：9:30-10:30 的票迟迟不推，10:30 后批量出现。

### 滞后源 3：momentum 累计涨幅门槛

- `scanner/analysis.py:483`：`if accumulated < 10: return None`
- **问题**：momentum 要求 5 日累计涨幅 ≥10%，今天刚启动但前期没涨的票永远进不了 momentum 池。
- **缓解**：这类票可走 new_face（若首次上榜）或 short_term（若今日涨幅 2-8%）。但若已上榜过且今日涨幅 >8%，4 个策略全部门槛不匹配，会漏推。

### 滞后源 4（参考，不在本次修改范围）

- 主循环 60s 间隔 + 单次扫描 10-18s = 基础时延 35-50s（必然，不调整）
- intraday 缓存 300s、minute 缓存 120s、market_index 缓存 180s（次要，可顺手调小）

## Proposed Changes

### Change 1：去掉 K 线 API 层缓存，保留编排层 TTL（核心）

**文件**：`scanner/api.py`

**改动**：将 `_kline_cache_ttl` 从 600 改为 0（禁用 API 层缓存），让 `fetch_kline` 每次都真正发请求，由编排层 `KLINE_REFRESH_TTL=300` 统一控制补拉频率。

**为什么**：双层缓存叠加是 K 线陈旧的最大元凶。去掉 API 层后，K 线新鲜度由编排层 300s 单独控制，最差从 600s 降到 300s。**不增加雪球 API 调用量**——编排层 TTL 不变，补拉频率不变，只是补拉时真正发请求而非命中 API 层旧缓存。

**具体**：
- `api.py:94`：`_kline_cache_ttl = 600` → `_kline_cache_ttl = 0`
- 保留 `_kline_cache` 数据结构（避免破坏 `fetch_kline` 内部逻辑），仅 TTL 设 0 使其永不命中

### Change 2：缩短编排层 KLINE_REFRESH_TTL

**文件**：`scanner/orchestrator.py`

**改动**：`KLINE_REFRESH_TTL` 从 300 改为 120。

**为什么**：300s 意味着盘中已缓存今日 bar 的票 5 分钟内不补拉。120s 让 K 线更及时反映盘中价格变化。配合 Change 1，K 线最差新鲜度从 600s 降到 120s。

**API 调用影响**：每只票补拉频率从每 5 分钟一次变成每 2 分钟一次，约 2.5 倍。但编排层只在"已含今日 bar 且超 TTL"时才补拉，且雪球 K 线 API 限流较宽（对比飙升榜），风险可控。

### Change 3：缩短 intraday 和 minute 缓存 TTL

**文件**：`scanner/api.py`

**改动**：
- `_INTRADAY_CACHE_TTL`：300 → 120（`api.py:392`）
- `_MINUTE_DATA_CACHE_TTL`：120 → 60（`api.py:396`）
- `_market_index_cache` TTL：180 → 60（`api.py:101`）

**为什么**：intraday 评分缓存 5 分钟，意味着分时强度加分 5 分钟内不更新。缩短到 2 分钟让盘中异动更快反映到 intraday_score。大盘指数 3 分钟缓存影响 market_env_bonus，缩短到 1 分钟。

**API 调用影响**：intraday 调用频率 2.5 倍、minute 2 倍、index 3 倍。但这些 API 单次响应小、限流宽，风险可控。

### Change 4：放宽早市惩罚

**文件**：`scanner/config.py`

**改动**：`EARLY_BONUS` 从 -5 改为 -2（`config.py:323`）。

**为什么**：-5 会把刚过 MIN_SCORE 的早盘票压到门槛下。-2 保留"早盘信号噪音大"的轻度抑制，但不再系统性压杀早盘异动。等效于 momentum 门槛从 21 降到 18、new_face 从 23 降到 20。

**风险**：可能引入早盘假信号（开盘冲高回落的票）。但 validator 交叉验证 + trend 硬过滤仍能挡住大部分噪音。

### Change 5：小幅下调 momentum 累计涨幅门槛

**文件**：`scanner/analysis.py`

**改动**：`if accumulated < 10: return None` → `if accumulated < 7: return None`（`analysis.py:483`）。

**为什么**：10% 门槛要求前期已有显著涨幅，今天刚启动的票无法进入 momentum。7% 让"温和启动+今日加速"的票能进 momentum 池。

**风险**：可能引入"假启动"票（累计涨幅不够但今日大涨）。但 validator 的 MA 多头/量能均匀/无顶背离三维交叉验证仍能过滤。

## Assumptions & Decisions

1. **不缩短主循环 60s 间隔**：雪球飙升榜 API 限流严格，缩短间隔高风险触发 429/断路器。
2. **不调整 MIN_SCORE**：MIN_SCORE 是策略核心门槛，调整需基于回测。本次通过放宽早市惩罚间接降低等效门槛。
3. **不调整 NEW_FACE_LOOKBACK_DAYS=3**：首次上榜判定不影响"涨起来了才推"的滞后感受。
4. **不调整 validator 的 pos_dims>=2**：交叉验证是质量保证，不动。
5. **K 线 API 层缓存设 0 而非删除**：保留数据结构避免破坏 `fetch_kline` 内部逻辑，未来需要时可恢复。
6. **不调整飞书 FEISHU_MIN_INTERVAL=300**：推送延迟不影响 display 本地展示，且飞书限流严格。
